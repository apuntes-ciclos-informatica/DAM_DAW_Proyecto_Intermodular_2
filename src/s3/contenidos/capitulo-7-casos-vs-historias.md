# _Casos de Uso_ vs _historias de usuario_

Conceptualmente ambas son muy similares ya que son herramientas para obtener los requisitos de un sistema y tienden a confundirse, pero lo hacen desde perspectivas y propósito diferentes.
| Característica         | Casos de Uso                                                                                                                                                                                                 | Historias de Usuario                                                                                                                      |
|------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------|
| Propósito rincipal    | Describir la interacción completa entre un actor y el sistema .                                                                                                                             | Iniciar una conversación sobre una necesidad del usuario .                                                                 |
| Nivel de detalle       | Alto y exhaustivo. Incluye flujos alternativos, excepciones y precondiciones.                                                                                                                               | Bajo o medio. Se enfoca en el "qué" y el "porqué", dejando el "cómo" para después.                                                       |
| Formato                | Documento técnico, diagramas UML, tablas estructuradas.                                                                                                                                                     | Texto simple en una tarjeta (física o virtual) con el formato "Como..., quiero..., para...".                                             |
| Enfoque                | Centrado en el sistema y sus procesos internos.                                                                                                                                                             | Centrado en el usuario y el valor que recibe.                                                                                            |
| Orientación            | Técnica y prescriptiva. Sirve como un contrato detallado para el desarrollo.                                                                                                                                | Colaborativa y descriptiva. Fomenta el diálogo y la flexibilidad.                                                                        |
| Cuándo se crea         | Generalmente se definen al inicio del proyecto, en la fase de análisis.                                                                                                                                     | Se escriben y refinan continuamente a lo largo de todo el proyecto.                                                                      |
| Ejemplo Detallado      | "El sistema valida las credenciales del usuario." 1. El usuario introduce email y contraseña. 2. El sistema verifica que el formato del email sea válido. 3. El sistema busca el email en la base de datos. 4. Flujo alternativo: Si no lo encuentra, muestra "Usuario no registrado". 5. El sistema compara el hash de la contraseña introducida con el almacenado. 6. Flujo alternativo: Si no coinciden, muestra "Contraseña incorrecta". 7. Si coinciden, inicia la sesión. | "Como usuario registrado, quiero iniciar sesión con mi email y contraseña para poder acceder a mi panel de control." (Los detalles sobre mensajes de error y validaciones se discuten y se añaden después en los criterios de aceptación). |
